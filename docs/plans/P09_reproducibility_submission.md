## 1. Мета, межі та два статуси готовності

Інший виконавець має отримати ті самі дослідницькі результати та звітні матеріали,
починаючи з окремої чистої копії репозиторію й задокументованих залежностей.
Фінальний комплект має містити код, джерела, результати, інструкцію та чесний
перелік невиконаних вимог. Сам факт наявності PDF не доводить відтворюваності.

Розділяємо:

- **technical_reproducibility_status / технічна K4:** повний запуск, незалежне
  повторення, перевірений renderer і цілісний комплект; PASS лише за всіма доказами.
- **course_submission_status:** open, доки обов'язкові вимоги курсу не виконані
  або немає документованого погодження конкретного відхилення. Технічний PASS
  не закриває автоматично вимогу3–5 citing/checking або реальну репетицію.
  Термін «K4» у фінальному документі завжди уточнюється; загальна готовність
  до здачі не оголошується за одного лише технічного PASS.

У P09 повторно виконуємо вже визначений аналіз. Нових моделей, гіпотез, іншого
датасету чи підбору специфікацій не плануємо. Виправлення виявлених помилок
допустимі лише з описом причини, повторними перевірками й аудитом залежних
результатів. Протокол/config/аналітичний uv.lock зберігаємо; не оновлюємо пакети
заради новіших версій. Завантаження роботи в систему курсу, повідомлення викладачу
й публікація репозиторію не входять до цієї фази без окремого доручення.

## 3. Послідовність роботи

### P09.1. Контракт повного запуску та baseline — S

1. Перелічити кроки: preflight → notebook00 →01 →02 →03 →04 →05 → reports →
   повний pytest → звірка чисел/артефактів → підсумковий статус. Аналітичні ноутбуки послідовні.
2. Визначити інтерфейс `scripts/run_project.py`, наприклад повний запуск за
   замовчуванням і `--analysis-only`. Назви прапорців уточнюються в реалізації.
   Analysis-only не видавати за повний PASS; пропущені кроки записувати явно.
3. Визначити обов'язкові входи/виходи, timeout кожного кроку, fail-fast, журнал
   stdout/stderr та метадані. Не робити складний resume-кеш у першій версії:
   невдалий повний запуск повторюється з початку після усунення причини.
4. Записувати running до preflight; ready лише після перевірки всіх заявлених
   виходів. На помилку, timeout або переривання — ненульовий exit і failed або
   interrupted, без використання старого ready. Старі журнали не є доказом нового run.

**Вихід:** контракт runner, baseline hashes; короткий CLI у scripts/, спільна
логіка в src/parentedu/reproducibility.py. Координатор.

### P09.2. Runner ноутбуків із чистими ядрами — M

1. Реалізувати послідовне виконання через nbclient/nbconvert з наявного lock.
   Кожен notebook отримує нове ядро; вихідні notebook не змінюються. Виконані
   копії й окремі логи записуються в outputs/executed і outputs/logs або їх
   підкаталоги run_id. Наявний workflow не має залежати від outputs попереднього ядра.
2. Перевірити фактичний sys.executable, sys.prefix і parentedu.__file__: усі
   належать .venv/src саме поточної копії. Kernelspec установити з --prefix .venv;
   локальний пошук ядра/явний kernel argv має виключати глобальне старе ядро.
3. Ізолювати cwd/env кожного процесу; не передавати приватні env/credentials у логи.
   Зафіксувати UTC початку/кінця, тривалість, команди, exit codes, Python/пакети,
   seed, Git HEAD/dirty та source/input/output hashes. Перевірити clean стан
   окремо на старті та після запуску, не вимагати старого commit у старих фазових логах.
4. Clean-run preflight перевіряє джерела/конфіг/середовище і зафіксований baseline,
   але не вимагає ще не створених P03–P08 outputs або локальних ready-логів.
   Це відрізняється від перевірки чинності baseline у початковій робочій копії.
   Після кожного notebook перевіряти не лише exit code, а й ready його workflow,
   очікувані файли та чинність hashes. Фазовий marker має бути заново створений
   або оновлений у межах start/end поточного кроку; його hash записується в receipt
   поточного run_id. Старий ready, навіть із правильними CSV, не зараховується.
   Додавання run_id до історичних workflow не обов'язкове: зв'язування виконує runner.
   Після05 — чинний K3 seal/review. При
   відмінних final outputs зупинитися для нового аудиту; не копіювати старий
   audit_status, не перевипускати K3 автоматично, не послаблювати seal-перевірку.
5. Протестувати суттєві випадки: порядок/окремі ядра, неправильний interpreter,
   провал посередині без запуску наступних кроків, timeout, stale evidence і
   старий ready. Інтеграційний success перевіряється реальним повним запуском.

**Вихід:** runner і змістові тести; локальний журнал одного успішного запуску.
Координатор; reviewer перевіряє відсутність прихованого стану.

### P09.4. Чиста копія та незалежне повторення — M

1. Після реалізації й фіксації candidate commit створити окремий локальний clone
   у новому абсолютному шляху, бажано з пробілами. Власну робочу .venv чи data

   як baseline порівняння, але прибрати з робочих output-каталогів до запуску,
   щоб жоден етап не міг видати старі tracked CSV/PDF за нову генерацію.
   Текст docs/final_conclusions.md можна зберегти як tracked baseline, але05 має
   перегенерувати його і свіжий conclusions marker; K3 не переписується автоматично.
2. Заново створити .venv через uv sync --locked, локальне ядро й окремий renderer;
   підтвердити location імпортів. Зафіксувати candidate HEAD, первинний Git state
   і всі навмисні вилучення baseline outputs. Передача журналів основного run
   до чистої копії заборонена; кожна фаза має створити власні метадані.
3. Основна перевірка — нове завантаження UCI за pinned SHA з відсутнього raw cache.
   Не переписувати історичний docs/data_provenance.json новою датою завантаження;
   нова дата належить локальному acquisition manifest. При недоступності мережі
   дозволений окремо позначений запуск із hash-verified raw seed-cache, але він
   підтверджує лише перерахунок із кешу, не успішне завантаження з нуля.
4. Незалежний reviewer запускає описані команди з цієї копії та звіряє результати.
   Окремо засвідчити незалежного виконавця, окремий шлях і чисте середовище;
   це не перевірка на іншій фізичній машині й не незалежна нова вибірка даних.
5. Після відтворення порівняти baseline і нові outputs. Якщо код із технічних
   причин потребує відсутнього файла, відновлювати кроком генерації, а не
   непозначеним копіюванням готових результатів.

**Вихід:** журнал clean-run, доказ acquisition/cache-mode, незалежний review.
Reviewer працює у власній копії; координатор не редагує її під час перевірки.
